# Wait:ON 시스템 설계

## 문서 정보

- 상위 문서: [`PROJECT_V2.md`](./PROJECT_V2.md), [`GAMEPLAY.md`](./GAMEPLAY.md)
- 문서 목적: 자원 흐름, 작업 대기열, 상태 변화, 이벤트 페이싱과 폭주 방지 규칙을 정의한다.
- MVP 기준: 고정된 병원 하루와 결정론적 규칙
- 후속 기준: 동일한 규칙 위에 제약 기반 운영 디렉터를 추가한다.

---

## 1. 시스템 설계 목표

Wait:ON의 시스템은 다음 경험을 만들어야 한다.

1. 사용자는 현재 병목의 원인을 설명할 수 있다.
2. 하나의 행동은 여러 지표에 이해 가능한 영향을 준다.
3. 같은 행동도 현재 병원 상태에 따라 결과가 달라진다.
4. 작은 실수가 연쇄적으로 퍼질 수 있지만 회복 불가능해지지 않는다.
5. 모든 핵심 상태는 저장하고 같은 결과로 복원할 수 있다.
6. 새로운 부서와 이벤트는 기존 규칙의 조합으로 추가할 수 있다.

---

## 2. 운영 경제: 시간과 처리 용량

Wait:ON에는 화폐가 없다. 시스템의 공통 단위는 **게임 시간과 시간당 처리 용량**이다.

### 흐름 모델

| 배관 비유 | Wait:ON 시스템 |
|---|---|
| 흐르는 물 | 환자와 처리 작업 |
| 파이프 | 외래, 검사실, 응급실, 수술실 |
| 수도꼭지 | 의료진, 시설, 남은 병상 |
| 밸브 | 배치, 일정, 대기열, 안내 |
| 막힘 | 수요가 처리 용량을 초과한 상태 |
| 넘침 | 대기, 피로와 안내 요청이 함께 증가하는 상태 |

### 자원 종류

1. **의료진 용량:** 역할, 배치, 일정과 피로도에 따라 달라진다.
2. **시설 용량:** 동시에 처리할 수 있는 작업 수와 가동 상태로 결정된다.
3. **병상 용량:** 병실 유형별 전체 병상과 남은 병상으로 관리한다.
4. **운영 시간:** 모든 작업과 일정이 공유하는 되돌릴 수 없는 자원이다.
5. **안내 용량:** 별도 화폐가 아니라 의료진 또는 운영 행동이 사용하는 짧은 시간 비용이다.

### 병목 정의

부서의 병목 압력은 다음 개념으로 계산한다.

```text
병목 압력 =
  대기 작업의 남은 처리시간 합계
  ÷ 현재 부서의 유효 처리 용량
```

유효 처리 용량이 0이면 병목 압력은 최고 단계로 처리한다. 사용자 화면에는 공식 대신 예상 대기, 대기 인원과 병목 원인을 보여준다.

## 3. 병원 상호작용 엔진

각 이벤트를 개별 코드로 만들지 않고 엔티티와 표준 효과의 조합으로 표현한다.

### 엔티티

- 환자
- 의료진
- 부서
- 시설
- 병상 풀
- 작업
- 일정
- 이벤트
- 평가 지표

### 표준 효과

| 효과 | 설명 |
|---|---|
| `enqueueTask` | 작업을 대기열에 추가 |
| `changeCapacity` | 부서 또는 시설 처리 용량을 일정 시간 변경 |
| `moveStaff` | 의료진 이동과 준비 작업 생성 |
| `shiftSchedule` | 예정 작업의 시작 시각 변경 |
| `occupyResource` | 시설이나 병상을 예약 또는 점유 |
| `releaseResource` | 예약 또는 점유 해제 |
| `changeMetric` | 지표에 원인과 함께 변화 적용 |
| `applyModifier` | 일정 시간 동안 피로·속도·가동 상태 변경 |
| `showGuidance` | 환자 안내 상태와 예상시간 갱신 |
| `createAlert` | 사용자에게 원인과 가능한 대응을 표시 |

### 상호작용 법칙

1. 이벤트와 작업은 엔티티의 상태를 표준 효과로 변경한다.
2. 상태 효과는 다른 효과의 조건과 강도를 바꿀 수 있다.
3. 엔티티가 다른 엔티티를 임의로 직접 수정하지 않는다.
4. 모든 상태 변화는 원인 ID를 가진다.
5. 한 원인은 같은 평가 항목을 한 번만 차감한다.

이 규칙은 복잡한 병원 연쇄를 제한된 조합으로 만든다.

```text
장비 점검
→ 검사실 용량 감소
→ 검사 작업 대기
→ 외래 결과 확인 지연
→ 안내 갱신 필요
```

## 4. 게임 시간과 업데이트 순서

### 시간

- 기본 속도에서 현실 시간 1초는 게임 시간 1분이다.
- 일시정지, 이벤트 선택, 튜토리얼과 결과 화면에서는 게임 시간이 흐르지 않는다.
- 2배속은 이벤트가 없고 운영 위험 상태가 아닐 때만 사용할 수 있다.
- 백그라운드 진입 시 즉시 일시정지한다.

### 결정론적 업데이트 순서

각 게임 시간 틱은 다음 순서를 따른다.

1. 사용자 행동 적용
2. 예약된 일정과 환자 도착 활성화
3. 대기 작업 조건 재평가
4. 자원 예약과 작업 시작
5. 진행 중인 작업의 남은 시간 감소
6. 완료 작업 처리와 자원 해제
7. 환자·의료진 상태 전이
8. 지표 변화 계산
9. 병목과 운영 압박 계산
10. 이벤트 또는 디렉터 평가
11. UI에 전달할 변화 기록 생성
12. 필요 시 저장 스냅샷 생성

같은 초기 상태, 난수 시드와 사용자 행동 순서는 항상 같은 결과를 만들어야 한다.

## 5. 작업 시스템

### 작업 상태

```text
scheduled
  → waiting
  → ready
  → reserved
  → running
  → completed
```

예외 상태:

- `blocked`: 실행 조건이 충족되지 않았고 사용자에게 이유를 보여줘야 함
- `cancelled`: 일정 변경으로 더 이상 실행하지 않음

### 작업 데이터

```ts
type Task = {
  id: string
  type: TaskType
  status: TaskStatus
  patientId?: string
  departmentId: string
  readyAt: number
  duration: number
  remaining: number
  priority: number
  requirements: Requirement[]
  dependencies: string[]
  reservedResourceIds: string[]
  blockedReason?: BlockedReason
  sourceEventId?: string
}
```

실행 조건을 함수나 클로저로 저장하지 않는다. 저장과 복구가 가능한 데이터로 표현한다.

### 조건 유형

- 게임 시각 도달
- 선행 작업 완료
- 환자 도착
- 필요한 역할의 의료진 사용 가능
- 필요한 시설 사용 가능
- 부서 운영 가능
- 병상 사용 가능
- 활성 이벤트 해결

### MVP 작업 유형

- 환자 도착
- 외래 진료
- 검사
- 외래 결과 확인
- 응급 이벤트 대응
- 수술
- 병상 배정
- 의료진 이동
- 의료진 휴식
- 환자 안내

### 대기열 우선순위

1. 활성 이벤트가 지정한 작업
2. 예정 시각을 넘긴 작업
3. 대기 허용시간에 가까운 작업
4. 먼저 생성된 작업

이 규칙은 게임의 가상 운영 규칙이며 실제 의료 우선순위를 나타내지 않는다.

### 조건 재평가

모든 프레임에 전체 작업을 검사하지 않는다.

- 자원 해제
- 작업 완료
- 의료진 이동 완료
- 시설 상태 변화
- 게임 시각 도달
- 이벤트 선택

위 상태 변화가 발생할 때 관련 대기 작업만 다시 평가한다. 고정 게임 틱은 누락된 평가를 보완한다.

## 6. 자원 예약과 동시성

여러 작업이 같은 시점에 실행 가능해져도 같은 의료진이나 시설을 동시에 사용할 수 없다.

### 원자적 예약

```text
모든 조건 확인
→ 필요한 자원을 임시 예약
→ 전부 성공하면 작업 시작
→ 하나라도 실패하면 전체 임시 예약 해제
```

### 예약 규칙

- 한 의료진은 동시에 하나의 작업만 수행한다.
- 한 시설 슬롯은 동시에 하나의 작업만 처리한다.
- 병상은 배정 확정 시 즉시 남은 수량에서 차감한다.
- 이동 중인 의료진은 출발 부서와 도착 부서 어느 쪽에도 처리 용량을 제공하지 않는다.
- 취소된 작업은 같은 틱 안에서 자원을 해제한다.

### 교착 방지

- 작업은 필요한 자원을 한 번에 예약한다.
- 일부 자원만 가진 채 다른 자원을 기다리지 않는다.
- 30게임분 이상 차단된 작업은 병목 경고 대상이 된다.

## 7. 상태 머신

### 환자

```text
scheduled
→ arrived
→ registered
→ waiting
→ in_service
→ transferring
→ completed
```

병상 이벤트 대상은 `waiting_for_bed` 상태를 추가로 사용할 수 있다.

### 의료진

```text
available
→ moving
→ preparing
→ working
→ available
```

휴식 시 `resting`, 일정 충돌 시 `schedule_conflict` 상태를 사용한다.

### 시설

```text
available
→ reserved
→ operating
→ available
```

점검 이벤트에는 `maintenance` 상태를 사용한다.

### 병상

MVP는 개별 침대 엔티티가 아니라 병실 유형별 수량을 사용한다.

```text
totalBeds
availableBeds
reservedBeds
```

`availableBeds + reservedBeds`는 `totalBeds`를 넘을 수 없다.

## 8. 피드백 루프

### 증폭되는 운영 루프

```text
대기 증가
→ 안내 요청 증가
→ 의료진 시간 소모
→ 처리 용량 감소
→ 추가 대기
```

```text
피로 증가
→ 처리 속도 감소
→ 대기 증가
→ 추가 업무
→ 피로 증가
```

### 안정화 루프

| 조건 | 시스템이 제공하는 복구 수단 |
|---|---|
| 한 부서 대기 4명 이상 | 병목 원인과 재배치 예상 효과 표시 |
| 의료진 피로 70 이상 | 휴식 교대 행동 강조 |
| 환자 안전 40 이하 | 새로운 고압 이벤트 억제 |
| 환자 안전 20 미만 | 시간 정지 후 복구 선택 |
| 안내 정확도 40 이하 | 오래된 안내 목록 표시 |
| 남은 병상 1개 이하 | 다음 수술 일정에 병상 위험 표시 |
| 고압 이벤트 2회 연속 | 현실 시간 최소 30초의 회복 구간 |

안정화 루프는 문제를 자동 해결하지 않는다. 사용자가 회복할 수 있는 정보와 선택을 제공한다.

### 연쇄 제한

- 이벤트 효과는 최대 두 단계의 하류 부서까지만 전파한다.
- 이벤트가 만든 지연은 새 고압 이벤트의 직접 트리거가 되지 않는다.
- 같은 `causeId`는 같은 지표를 한 번만 차감한다.
- 환자 한 명의 안내 요청은 추가 안내 이벤트를 생성하지 않는다.
- 피로도와 모든 점수형 지표는 0~100으로 제한한다.

## 9. 이벤트 선택과 트레이드오프

### 선택 조건

모든 운영 선택은 다음을 가진다.

- 즉시 효과
- 이후 발생할 수 있는 영향
- 개선되는 지표
- 악화될 수 있는 지표
- 적용 기간
- 실제 의료와 다름을 알리는 문구

### 허용되는 위험

- 대기 증가
- 일정 충돌
- 의료진 피로
- 시설 가동 중단
- 병상 부족
- 안내 정확도 하락

### 허용하지 않는 위험

- 사망
- 수술 실패
- 실제 증상 악화
- 치료 기회 상실
- 실제 의료진 판단을 모사하는 결과

### 단일 최적해 방지

- 동일한 선택의 효과는 현재 대기열과 일정에 비례한다.
- 의료진 재배치에는 이동·준비시간이 따른다.
- 안내에는 짧은 시간 비용이 있다.
- 병상 즉시 배정은 선호도와 향후 여유 병상에 영향을 준다.
- 휴식을 계속 미루면 처리 속도가 감소한다.

## 10. 이벤트 분배와 불운 방지

### MVP

- 발표와 첫 플레이테스트는 이벤트 순서와 난수 시드를 고정한다.
- 이벤트 6개가 정해진 페이싱 구간에 발생한다.
- 플레이어 선택만 결과 차이를 만든다.

### 반복 플레이

반복 플레이에서는 제약이 있는 셔플백을 사용한다.

```text
예정 이벤트 2개
돌발 이벤트 2개
환자 경험 이벤트 2개
```

규칙:

- 사용한 이벤트는 당일 셔플백에서 제거한다.
- 같은 부서 이벤트가 연속 발생하지 않는다.
- 고압 이벤트는 두 번 연속 발생하지 않는다.
- 모든 핵심 시스템은 하루에 최소 한 번 등장한다.
- 셔플백은 다음 날 다시 구성한다.
- 난수 시드는 저장 데이터에 포함한다.

순수 확률로 어려운 사건이 계속 발생하거나, 특정 시스템을 전혀 경험하지 못하는 상태를 허용하지 않는다.

## 11. 운영 디렉터

운영 디렉터는 생성형 AI가 아니라 병원 상태를 관찰하는 규칙 기반 상태 머신이다.

### 입력

- 부서별 병목 압력
- 장기 대기 환자 수
- 활성 이벤트 수
- 의료진 평균 및 최고 피로도
- 환자 안전
- 안내 정확도
- 남은 병상
- 최근 이벤트와 해결시간

실제 환자정보나 사용자의 신체·감정 상태는 입력으로 사용하지 않는다.

### 상태

```text
buildup → peak → recovery → buildup
```

#### 전개

- 일반 환자와 예정 일정 활성화
- 하나의 병목을 형성
- 다가오는 일정 충돌을 예고

#### 정점

- 핵심 이벤트 하나 활성화
- 새로운 고압 이벤트 억제
- 최대 두 부서에 연쇄 영향 허용

#### 회복

- 현실 시간 30~45초 동안 새로운 고압 이벤트 금지
- 환자 안내, 의료진 휴식과 병상 정리 기회 제공
- 사용자가 병원 상태를 재평가하도록 유도

### 운영 압박도

내부 `pressure`는 0~100으로 계산한다.

| 구간 | 의미 |
|---|---|
| 0~39 | 안정 |
| 40~69 | 전개 |
| 70~100 | 정점 |

사용자에게 숫자를 직접 보여주기보다 압박의 상위 세 원인을 표시한다.

### 금지

- 플레이를 잘한다는 이유로 불합리한 사고 생성
- 선택 결과를 사후에 몰래 변경
- 사용자의 입력이 느리다는 이유로 불이익 부여
- 실제 의료 판단을 디렉터 선택처럼 표현

## 12. 행동 피드백과 원인 추적

모든 상태 변화는 다음 정보를 기록한다.

```ts
type StateChange = {
  id: string
  causeId: string
  causeType: "player" | "schedule" | "event" | "system"
  targetId: string
  field: string
  before: number | string
  after: number | string
  gameTime: number
  messageKey: string
}
```

이 기록은 다음에 사용한다.

- 행동 직후 변화 표시
- 부서 병목 원인 설명
- 하루 결과의 잘한 결정과 개선점
- 저장 복구 검증
- 플레이테스트 분석

사용자에게 보이지 않는 계산도 결과에 영향을 주면 이해 가능한 원인으로 요약해야 한다.

## 13. 저장과 복구

### 저장 대상

- 게임 시각과 속도
- 난수 시드
- 모든 엔티티 상태
- 작업 대기열과 의존성
- 자원 예약
- 이벤트 셔플백과 디렉터 상태
- 지표와 상태 변화 기록
- 튜토리얼 진행

### 저장 원칙

- 사용자 행동은 메모리 상태에 즉시 반영한다.
- 저장은 비동기로 수행하고 UI를 멈추지 않는다.
- 행동 확정 직후 최신 스냅샷을 요청한다.
- 15초마다 보조 스냅샷을 만든다.
- 마지막 정상 스냅샷과 이전 정상 스냅샷을 유지한다.
- 저장 중 새 상태가 생기면 완료 후 최신 상태를 한 번 더 저장한다.

### 복구

1. 최신 저장본의 스키마와 체크섬 확인
2. 실패하면 이전 정상 저장본 확인
3. 작업 예약과 엔티티 점유 관계 검증
4. 파생 값 재계산
5. 저장 당시 일시정지 상태로 화면 복구

이탈 중에는 병원 시간이 흐르지 않는다.

## 14. 시스템 수용 기준

1. 같은 초기 상태와 행동 순서는 같은 결과를 만든다.
2. 실행 불가능한 작업에는 저장 가능한 차단 이유가 있다.
3. 같은 자원을 두 작업이 동시에 예약할 수 없다.
4. 상태 변경 후 관련 작업만 재평가된다.
5. 이벤트 연쇄가 두 단계 이상 전파되지 않는다.
6. 환자 안전 40 이하에서 고압 이벤트가 추가되지 않는다.
7. 환자 안전 20 미만에서 복구 선택이 제공된다.
8. 같은 원인으로 지표가 중복 차감되지 않는다.
9. 저장 후 작업·예약·디렉터 상태를 동일하게 복원한다.
10. 모든 결과 화면 설명은 상태 변화 기록에서 생성할 수 있다.
