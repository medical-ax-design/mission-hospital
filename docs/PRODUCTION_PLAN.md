# Wait:ON MVP 제작 계획

## 문서 정보

- 제품 기준: [`PROJECT_V2.md`](./PROJECT_V2.md)
- 게임 규칙: [`GAMEPLAY.md`](./GAMEPLAY.md)
- 기술 기준: [`TECHNICAL_DESIGN.md`](./TECHNICAL_DESIGN.md)
- 문서 목적: 5일 발표용 프로토타입의 순서, 범위와 완료 조건을 정의한다.

---

## 1. 제작 원칙

1. 병원 전체보다 첫 닫힌 루프를 먼저 만든다.
2. 아트보다 규칙과 피드백을 먼저 검증한다.
3. 고정 시나리오로 결과 재현성을 확보한다.
4. 자동 저장과 이어하기를 마지막에 붙이지 않는다.
5. 기능 수보다 인과관계의 명확성을 우선한다.
6. 실제 의료 검토가 필요한 콘텐츠를 임의로 확장하지 않는다.

---

## 2. 제작 마일스톤

### 마일스톤 1: 닫힌 루프

범위:

- 외래
- 검사실
- 환자 3명
- 의사 1명과 검사 담당자 1명
- 의료진 재배치
- 대기시간과 만족도
- 행동 전 예상 영향과 행동 후 결과

완료 조건:

- 재배치가 두 부서에 다른 영향을 줌
- 사용자가 변화 원인을 확인
- 같은 상태와 입력이 같은 결과를 만듦

### 마일스톤 2: 작업과 자원

범위:

- 조건부 작업 대기열
- 의료진·시설 원자적 예약
- 일정
- 피로도
- 차단 이유

완료 조건:

- 중복 예약이 발생하지 않음
- 차단된 작업의 이유 표시
- 작업 상태 저장과 복구

### 마일스톤 3: 병원 하루

범위:

- 응급실과 수술실
- 간이 병상 자원
- 환자 12명
- 이벤트 6개
- 9분 페이싱

완료 조건:

- 전개·정점·회복 흐름
- 이벤트 연쇄 두 단계 제한
- 강제 게임 오버 없음

### 마일스톤 4: 중단과 복귀

범위:

- 상태 변경 직후 저장
- 15초 주기 저장
- 백그라운드 일시정지
- 잠시 나가기
- 이어하기
- 이전 정상 저장본

완료 조건:

- 주요 상태에서 중단 후 동일한 위치 복귀
- 저장 실패가 플레이를 멈추지 않음

### 마일스톤 5: UX와 발표 완성도

범위:

- 병원 단면
- 랜드마크와 병목 표시
- 튜토리얼
- 하루 결과
- 모바일 접근성
- 임시 또는 최종 아트

완료 조건:

- 3분 안에 첫 결정
- 5초 안에 병목 발견
- 무음·모션 줄이기 지원
- 고정 데모 시나리오 완주

---

## 3. 5일 작업 순서

| 일자 | 핵심 산출물 |
|---|---|
| 1일차 | 프로젝트 초기화, 순수 게임 엔진, 닫힌 외래·검사 루프, 저장 봉투 |
| 2일차 | 작업 큐, 자원 예약, 의료진 일정, 상태 스냅샷 왕복 테스트 |
| 3일차 | 응급실·수술실·병상, 고정 이벤트와 지표 |
| 4일차 | 병원 단면 UI, 행동 피드백, 자동 저장 트리거와 중단·복귀 |
| 5일차 | 튜토리얼, 결과, 접근성, 플레이테스트 수정, 발표 시나리오 |

기능이 지연되면 아트와 장식 효과를 먼저 줄이고 닫힌 루프와 저장 기능은 유지한다.

---

## 4. 작업 영역

### 기획

- 규칙과 수치
- 이벤트 선택
- 콘텐츠 문구
- 안전 검수

### 프런트엔드

- 모바일 화면
- 병원 단면
- 상태 카드
- 이벤트와 결과 UI

### 게임 시스템

- 시계
- 작업 스케줄러
- 자원 예약
- 상태 전이
- 지표와 변화 기록

### 아트

- 부서 랜드마크
- 환자와 의료진 아이콘
- 상태 효과
- 시간대 배경

### QA와 플레이테스트

- 규칙 테스트
- 저장 복구
- 모바일 접근성
- 의료 오인과 메시지 검토

역할은 팀 인원에 따라 겸임하되 산출물 책임은 작업 영역별로 구분한다.

---

## 5. 범위 축소 순서

일정이 부족하면 다음 순서로 줄인다.

1. 고급 조명과 구름
2. 캐릭터 애니메이션 수
3. 2배속
4. 이벤트 6개 중 반복 성격이 강한 2개
5. 결과 피드백 문구 유형

유지해야 하는 항목:

- 외래·검사 닫힌 루프
- 한 선택의 장단점
- 병목 원인 표시
- 자동 저장과 이어하기
- 강제 게임 오버 없음
- 의료 안전 고지

---

## 6. 변경 관리

게임 방향 변경은 다음 순서로 기록한다.

1. 바꾸려는 문제
2. 관찰 또는 근거
3. 선택한 변경
4. 영향을 받는 문서
5. 검증 방법

상위 원칙이 바뀌면 `PROJECT_V2.md`를 먼저 수정하고 하위 문서를 동기화한다.

---

## 7. 완료 정의

MVP는 다음 조건을 모두 만족할 때 발표 가능하다.

- 고정 하루를 처음부터 결과까지 플레이
- 핵심 행동의 예상 영향과 실제 결과 표시
- 작업과 자원 중복 없음
- 이벤트 연쇄 제한
- 잠시 나가기와 이어하기
- 모바일 세로 화면 지원
- 무음과 모션 줄이기 지원
- 실제 의료 판단 기능 없음
- 자동 테스트 통과
- 최소 5명 사용성 테스트의 S0·S1 문제 없음
