# 제품 요구사항 문서(PRD)

## 1. 제품 목표

4일 프로토타입은 다음 폐쇄 루프를 시연한다.

```text
검사·수술 항목 등록
→ 준비 프로토콜 작성·게시
→ 가상 환자 일정 생성
→ 게시 프로토콜 자동 배정
→ 환자 준비 작업 수행
→ 의료진 예외 대시보드 반영
```

## 2. 릴리스 범위

### 포함

- 의료진 로그인
- 환자 데모 계정 로그인
- 검사·수술 카탈로그 검색 및 등록
- 이름, 구분, 담당 부서, 선택적 외부 코드 관리
- 단계별 준비 프로토콜 작성
- 초안, 게시, 종료 상태
- 프로토콜 버전 관리
- 가상 환자 준비 케이스 생성
- 게시된 프로토콜 자동 배정 및 스냅샷 생성
- 환자의 준비 작업 확인·완료·도움 요청
- 의료진 예외 대시보드
- 감사 로그
- Vercel, OCI, Supabase 기반 배포 구조

### 제외

- 실제 환자정보
- 실병원 SSO
- EMR·OCS 실연동
- 실제 문자·푸시 알림
- 보호자 초대 인증
- 의료진 간 전자결재
- 복잡한 조건식 편집기
- AI 요약 및 챗봇
- 통계적 효과 분석

## 3. 역할과 권한

| 역할 | 설명 | 주요 권한 |
|---|---|---|
| ADMIN | 프로토타입 관리자 | 항목 등록, 프로토콜 작성·게시·종료, 감사 로그 조회 |
| STAFF | 의료진 | 항목 검색, 환자 케이스 생성, 상태 확인, 도움 요청 처리 |
| PATIENT | 가상 환자 | 본인 준비 작업 조회 및 상태 변경 |

프로토타입에서는 ADMIN이 작성과 게시를 모두 수행할 수 있다. 운영 환경에서는 작성자와 승인자 분리를 권장한다.

## 4. 기능 요구사항

### FR-CAT: 검사·수술 카탈로그

#### FR-CAT-001 항목 검색

의료진은 이름, 외부 코드, 담당 부서로 검사·수술 항목을 검색할 수 있어야 한다.

인수 조건:

- 부분 일치 검색을 지원한다.
- 비활성 항목은 기본 검색 결과에서 제외한다.
- 결과에 이름, 검사·수술 구분, 담당 부서, 외부 코드 유무를 표시한다.
- 검색 결과가 없으면 새 항목 등록 행동을 제공한다.

#### FR-CAT-002 항목 등록

ADMIN은 검사 또는 수술 항목을 등록할 수 있어야 한다.

필수값:

- `procedure_type`: `EXAM` 또는 `SURGERY`
- `name`
- `department`

선택값:

- `external_code`
- `description`

인수 조건:

- DB가 UUID 기본키를 자동 생성한다.
- 동일 조직 내 동일한 외부 코드는 중복 등록할 수 없다.
- 외부 코드가 없는 항목도 등록할 수 있다.
- 이름 중복 시 저장 전 경고하되, 담당 부서 또는 프로토콜이 다른 경우 관리자가 계속할 수 있다.

#### FR-CAT-003 항목 비활성화

사용 중인 항목은 삭제하지 않고 비활성화한다.

인수 조건:

- 기존 환자 케이스와 감사 기록은 유지한다.
- 비활성 항목으로 신규 케이스를 만들 수 없다.

### FR-PRO: 준비 프로토콜

#### FR-PRO-001 프로토콜 초안 작성

ADMIN은 카탈로그 항목에 준비 프로토콜 초안을 생성할 수 있어야 한다.

프로토콜 필드:

- 제목
- 버전
- 적용 기준 설명
- 환자용 주의문
- 내부 메모

#### FR-PRO-002 준비 단계 구성

각 단계는 다음 정보를 가진다.

- 환자에게 표시할 제목과 설명
- 기준 시점: 검사·수술 시각 기준 며칠 또는 몇 시간 전후
- 필수 여부
- 환자 응답 방식
- 도움이 필요할 때 안내할 연락 문구
- 정렬 순서

지원 응답 방식:

- `ACKNOWLEDGE`: 확인
- `COMPLETE`: 완료
- `YES_NO`: 예·아니오
- `HELP_REQUEST`: 도움 요청
- `INFORMATION_ONLY`: 읽기 전용

#### FR-PRO-003 게시

ADMIN은 유효한 초안을 게시할 수 있어야 한다.

인수 조건:

- 단계가 하나 이상 있어야 한다.
- 모든 필수 필드가 입력돼야 한다.
- 동일 항목에 동시에 게시 상태인 프로토콜은 하나만 존재한다.
- 게시 시 작성자, 게시자, 게시 시각을 기록한다.
- 게시된 내용은 수정할 수 없다.

#### FR-PRO-004 새 버전

게시된 프로토콜의 변경은 새 초안 버전을 생성해 수행한다.

인수 조건:

- 직전 버전의 내용을 복제한다.
- 새 버전 게시 시 기존 게시 버전은 종료된다.
- 기존 환자 케이스의 스냅샷은 변경되지 않는다.

### FR-CASE: 환자 준비 케이스

#### FR-CASE-001 가상 환자 일정 생성

STAFF는 가상 환자 계정, 환자 표시명, 검사·수술 항목, 예정 시각을 입력해 준비 케이스를 생성할 수 있어야 한다.

인수 조건:

- 가상 데이터임을 화면에 표시한다.
- PATIENT 역할의 가상 계정을 케이스에 연결한다.
- 항목의 현재 게시 프로토콜을 자동 선택한다.
- 게시 프로토콜이 없으면 케이스 생성을 차단하고 `프로토콜 미등록` 오류를 반환한다.

#### FR-CASE-002 프로토콜 스냅샷

케이스 생성 시 게시 프로토콜과 단계 내용을 환자 케이스 작업으로 복사한다.

인수 조건:

- 이후 원본 프로토콜이 종료돼도 환자 작업은 유지된다.
- 각 작업에는 원본 프로토콜 ID, 버전과 단계 ID를 기록한다.
- 마감 시각은 검사·수술 예정 시각과 단계 오프셋으로 계산한다.

#### FR-CASE-003 케이스 상태

케이스 상태:

- `NOT_STARTED`
- `IN_PROGRESS`
- `NEEDS_ATTENTION`
- `READY`
- `CANCELLED`
- `COMPLETED`

상태는 작업 상태에서 계산한다. 계산 결과를 `preparation_cases.status`에 함께 저장하고 작업 상태를 변경하는 트랜잭션에서 갱신한다. 단, 시간이 지나 발생하는 `OVERDUE`는 조회 시점에 계산하므로 대시보드는 저장된 케이스 상태만 신뢰하지 않는다. 취소와 완료는 명시적 명령으로 처리한다.

### FR-PAT: 환자 경험

#### FR-PAT-001 현재 작업

환자는 현재 수행해야 할 작업 하나를 가장 먼저 확인해야 한다.

인수 조건:

- 큰 글씨와 단일 주요 행동을 사용한다.
- 전체 일정과 완료 작업은 보조 화면에서 확인한다.
- 색상 없이도 상태를 구분한다.

#### FR-PAT-002 작업 응답

환자는 프로토콜이 허용한 응답만 제출할 수 있다.

인수 조건:

- 완료 시각과 응답자를 기록한다.
- 환자가 수정할 수 있는 응답은 명확한 취소 행동을 제공한다.
- 의료진 판단이 필요한 응답은 `NEEDS_REVIEW` 상태가 된다.

#### FR-PAT-003 도움 요청

환자는 준비 단계에서 도움을 요청할 수 있다.

인수 조건:

- 자유서술 의료상담 대신 미리 정의된 도움 유형을 선택한다.
- 도움 요청은 의료진 대시보드에 즉시 표시된다.
- 서비스가 긴급 의료 대응 채널이 아님을 표시한다.

### FR-DASH: 의료진 대시보드

#### FR-DASH-001 예외 우선 목록

의료진은 다음 순서로 환자를 확인한다.

1. 의료진 확인 필요
2. 도움 요청
3. 기한 경과 미완료
4. 아직 시작하지 않음
5. 정상 진행
6. 준비 완료

#### FR-DASH-002 필터

- 날짜
- 검사·수술
- 담당 부서
- 케이스 상태
- 도움 요청 유무

#### FR-DASH-003 상세

환자 상세에서 다음을 확인한다.

- 예정 검사·수술
- 사용된 프로토콜과 버전
- 단계별 상태와 응답 시각
- 도움 요청
- 의료진 처리 기록

### FR-AUD: 감사 로그

다음 행동을 기록한다.

- 카탈로그 항목 생성·수정·비활성화
- 프로토콜 생성·게시·종료
- 환자 케이스 생성·취소
- 환자 작업 상태 변경
- 도움 요청 처리

감사 로그는 일반 UI에서 수정·삭제할 수 없다.

## 5. 비기능 요구사항

### NFR-001 보안

- 모든 쓰기 요청은 인증돼야 한다.
- 역할별 권한을 API와 DB에서 검증한다.
- Supabase 서비스 키와 DB 비밀번호를 브라우저에 노출하지 않는다.

### NFR-002 접근성

- 모바일 환자 화면은 200% 확대에서도 주요 행동이 가려지지 않는다.
- 터치 대상은 최소 44×44 CSS 픽셀을 목표로 한다.
- 상태를 색상만으로 전달하지 않는다.
- 핵심 문장은 읽기 쉬운 한국어로 작성한다.

### NFR-003 추적성

- 모든 도메인 엔터티는 UUID와 생성·변경 시각을 가진다.
- 게시된 프로토콜과 환자 스냅샷의 관계를 추적할 수 있어야 한다.

### NFR-004 신뢰성

- 같은 요청의 중복 전송으로 작업이 중복 완료되지 않아야 한다.
- 게시 전환은 하나의 DB 트랜잭션으로 처리한다.

### NFR-005 성능 목표

프로토타입 기준:

- 검색 API p95 500ms 이하
- 대시보드 첫 데이터 응답 p95 1초 이하
- 환자 작업 상태 변경 p95 500ms 이하

## 6. 핵심 지표

프로토타입 사용성 지표:

- 의료진이 3분 안에 항목 검색부터 프로토콜 게시까지 완료
- 환자가 별도 설명 없이 현재 작업 완료
- 도움 요청이 의료진 화면에 반영
- 프로토콜 새 버전 게시 후 기존 환자 작업이 유지
- 테스트 참여자가 서비스를 의료판단 시스템으로 오해하지 않음

운영 단계 후보 지표:

- 준비 작업 확인률
- 기한 내 완료율
- 도움 요청 처리시간
- 검사 전날 미확인 환자 비율
- 프로토콜별 이탈 단계

준비 완료율을 검사 가능 여부 또는 임상 성과와 동일하게 해석하지 않는다.

## 7. 데모 시나리오

1. ADMIN이 `대장내시경`을 검색한다.
2. 결과가 없어 새 검사 항목을 등록한다.
3. 준비 프로토콜 v1을 만들고 4개 단계를 게시한다.
4. STAFF가 `68세 가상 환자 김환자`의 검사 일정을 생성한다.
5. 시스템이 v1을 환자 작업으로 복사한다.
6. 환자가 전날 식사 작업을 완료하고 장정결제 단계에서 도움을 요청한다.
7. 의료진 대시보드에 김환자가 최상단으로 표시된다.
8. ADMIN이 v2를 게시해도 김환자의 작업은 v1로 유지된다.
