# 보안·개인정보·의료 안전 기준

## 1. 범위

프로토타입은 실제 환자정보를 처리하지 않는다. 모든 환자명, 일정, 응답은 가상 데이터다.

실제 병원 도입은 별도 개인정보 영향평가, 병원 정보보안 검토, 법무 검토, 접근통제 설계와 운영계약 이후 진행한다.

## 2. 데이터 분류

| 등급 | 예 | 프로토타입 |
|---|---|---|
| 공개 | 서비스 소개 | 허용 |
| 내부 | 프로토콜 초안, 내부 메모 | 가상 데이터만 |
| 개인정보 | 이름, 연락처, 생년월일 | 사용 금지 |
| 민감정보 | 진단, 처방, 검사 결과 | 사용 금지 |
| 비밀정보 | 토큰, DB 비밀번호, 서비스 키 | 저장소 커밋 금지 |

## 3. 의료 안전 경계

- 서비스는 준비 작업 수행 상태를 관리한다.
- `READY`는 임상적 검사 가능 판정이 아니다.
- 환자가 약물 관련 질문에 답해도 서비스가 중단·복용 결정을 내리지 않는다.
- 병원이 승인한 지침이 없으면 안내를 생성하지 않는다.
- 생성형 AI를 의료지침 작성·변경·승인 경로에 사용하지 않는다.
- 환자 화면에 응급상황 대체 서비스가 아님을 표시한다.
- 음식·약·행동 검색은 허가 또는 안전 결과를 반환하지 않는다.
- 공식 제한과 일치하지 않는 검색은 `확인 전에는 제공하지 마세요`로
  처리하며 유사 규칙을 추론하지 않는다.
- 약물 검색은 복용·중단 지시를 생성하지 않는다.
- 보호자 질문은 의료진에게 자동 전송하지 않고 답변을 저장하지 않는다.

### AI 치료 과정 미디어

- AI 미디어 카드에는 `AI로 재구성한 일반 과정`과 `현재 환자의 실시간
  영상이 아닙니다`를 상시 표시한다.
- 장면에 환자 식별정보, 환자 얼굴, 출혈·절개·장기·수술 부위 등 자극적인
  실제 의료 행위를 포함하지 않는다.
- 미디어로 치료 예상 시간이나 결과를 암시하거나 추론하지 않는다.
- AI 미디어는 병원이 제공한 치료 상태를 변경·예측하거나 병원 확인을
  대신 검증하지 않는다.
- 영상이 없거나 재생되지 않으면 정지 포스터를, 포스터도 실패하면
  단계명이 있는 비자극적 기본 장면을 반드시 제공한다.
- 미디어 실패와 무관하게 병원 상태, 일반 과정 타임라인과 안전 고지를
  텍스트로 계속 확인할 수 있어야 한다.

## 4. 인증

- Supabase Auth를 사용한다.
- 브라우저는 짧은 수명의 access token을 API에 전달한다.
- API는 JWKS 기반 검증 라이브러리로 서명, 발급자, 대상, 만료를 검증한다.
- 토큰 payload를 서명 검증 전에 신뢰하지 않는다.
- 비활성 프로필은 유효한 토큰이 있어도 접근을 거부한다.

## 5. 권한

권한은 세 계층에서 검증한다.

1. API route 역할 검사
2. 도메인 명령의 조직·소유권 검사
3. PostgreSQL RLS

`raw_user_meta_data`처럼 사용자가 변경 가능한 메타데이터를 권한 근거로 사용하지 않는다. 역할과 조직은 서버가 관리하는 프로필 또는 검증된 app metadata를 사용한다.

## 6. 비밀정보

### 브라우저에 허용

- Supabase URL
- Supabase publishable key
- 공개 API base URL

### 서버 전용

- PostgreSQL connection string
- Supabase secret/service role key
- JWT 검증 구성
- OCI 배포 인증정보

서버 전용 값에 `NEXT_PUBLIC_` 접두사를 사용하지 않는다.

## 7. 네트워크

- 모든 사용자·서비스 통신에 HTTPS를 사용한다.
- API와 PostgreSQL 연결에 SSL을 사용한다.
- 가능하면 `sslmode=verify-full`과 Supabase CA를 사용한다.
- DB 포트를 공개 인터넷의 임의 주소에 개방하지 않는다.
- OCI 보안 목록과 NSG는 필요한 인바운드 포트만 허용한다.

## 8. 입력 검증

- API 경계에서 DTO 스키마를 검증한다.
- 문자열 길이와 enum을 제한한다.
- HTML 입력을 허용하지 않고 일반 텍스트로 저장한다.
- 정렬 필드와 페이지 크기를 allowlist로 제한한다.
- raw SQL 문자열 결합을 사용하지 않는다.
- `response_data`는 response type별 JSON schema로 검증한다.

## 9. 감사 로그

기록 대상:

- 프로토콜 작성·게시·종료
- 검사·수술 항목 변경
- 환자 케이스 생성·취소
- 환자 응답
- 도움 요청 처리

원칙:

- 감사 로그는 일반 API로 수정·삭제하지 않는다.
- 요청 ID와 행위자를 기록한다.
- 비밀번호, access token, refresh token, DB 비밀번호를 기록하지 않는다.
- 환자 자유서술을 최소화한다.
- 제한 질문은 검색어와 자동 생성 질문만 기록한다.

## 10. 로그

구조화 로그 필드:

- timestamp
- level
- service
- environment
- request_id
- route
- status_code
- duration_ms
- actor_id 또는 익명 식별자

금지:

- Authorization header
- Cookie 전체
- DB connection string
- 환자 준비 안내의 민감한 자유서술

## 11. 위협과 대응

| 위협 | 대응 |
|---|---|
| 다른 조직 데이터 조회 | organization 검사, RLS |
| 게시 프로토콜 몰래 변경 | 불변 처리, 새 버전, 감사 로그 |
| 중복 클릭로 작업 중복 완료 | idempotency key |
| 서비스 키 노출 | OCI secret, Vercel server env, 브라우저 금지 |
| SQL injection | ORM parameter binding, 입력 검증 |
| 권한 상승 | 서버 관리 역할, JWT claim 검증 |
| 세션 탈취 | HTTPS, 짧은 access token, 로그아웃·만료 처리 |
| 가짜 의료지침 | 게시 권한, 승인 표시, AI 생성 금지 |
| 검색 결과를 섭취 허가로 오인 | 허가 상태 제거, 보수적 확인 필요 결과, 공식 출처 표시 |
| AI 교육 미디어를 실시간 환자 영상으로 오인 | AI·비실시간 상시 고지, 비식별·비자극 장면, 포스터·기본 장면 대체 |

## 12. 실제 환자정보 전환 전 필수 과제

- 최소 수집항목 정의
- 보유·파기 기간
- 위탁 및 제3자 제공 관계 검토
- 병원 SSO와 계정 수명주기
- MFA 요구 수준
- 관리자 승인 분리
- 접근로그 보존
- 백업 암호화와 복구시험
- 침해사고 대응 절차
- 환자·보호자 연결과 동의 철회
- 국내 의료·개인정보 관련 법률 자문

이 문서는 법률 자문을 대체하지 않는다.

## 13. 배포 비밀정보

운영 배포에서 다음 값은 Git, PR 본문, CI 로그와 컨테이너 이미지에
포함하지 않는다.

- OCI tenancy·compartment·instance OCID와 API 개인키
- SSH 개인키
- 실제 공인 IP와 운영 도메인 구성값
- Vercel 토큰
- Supabase `DATABASE_URL`과 서비스 역할 키

OCI 서버의 실제 `deploy/oci/.env`는 소유자만 읽을 수 있도록
`chmod 600`을 적용한다. 저장소에는 키와 값이 없는
`deploy/oci/.env.example`만 유지한다. API 컨테이너는 비루트
사용자로 실행하고 `3001` 포트를 호스트에 publish하지 않는다.
