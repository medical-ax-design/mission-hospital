# Wait:ON 식이·행동 제한 가이드 설계

## 1. 문서 목적

이 문서는 보호자가 환자의 수술·검사 과정에서 피해야 할 음식과 행동을 확인하고, 공개자료만으로 판단할 수 없는 내용을 질문 목록으로 정리하는 기능을 설계한다.

기존 병원 전산 이벤트·직원 운영 워크플로와 결합하지만 독립된 제한사항 콘텐츠 모듈로 구현한다.

24시간 발표용 프로토타입에서는 다음 두 사례를 제공한다.

- 위암 위절제 수술 후 식이·행동 제한
- 오전 대장내시경 검사 전 식이·금식·준비 제한

## 2. 제품 원칙

Wait:ON은 음식이나 행동을 허가하지 않는다.

사용자에게 `먹어도 됩니다`, `해도 됩니다`, `안전합니다`와 같은 허가·보증 표현을 제공하지 않는다. 앱은 다음 두 결과만 제공한다.

1. `지금은 제공하지 마세요`: 현재 단계와 병원 승인 지침에서 제한이 확인된 경우
2. `확인 전에는 제공하지 마세요`: 공개자료 또는 현재 환자 정보만으로 판단할 수 없는 경우

검색 결과가 없거나 적용 조건을 확정할 수 없으면 두 번째 결과를 사용한다. AI 또는 클라이언트가 허용 여부를 추론하지 않는다.

## 3. 사용자 가치

### 보호자

- 환자가 원하는 음식이나 행동을 먼저 확인한다.
- 일반적인 제한과 환자별 확인 필요 사항을 구분한다.
- 근거와 적용 시점을 확인한다.
- 해결되지 않은 질문을 회진·상담 전에 한 번에 정리한다.

### 직원

- 반복되는 일반 질문을 병원 승인 콘텐츠로 안내한다.
- 개별 판단이 필요한 질문만 보호자와 상담한다.
- 공식 안내를 다시 입력하지 않는다.
- 필요할 때 특정 환자에게 적용할 추가 제한만 선택적으로 등록한다.
- 오래되거나 잘못된 공식 안내는 수정하지 않고 갱신 필요로 신고한다.

## 4. 범위

### 4.1 포함

- 발표자 전용 데모 시나리오 선택
- 위암 위절제 수술 시나리오
- 오전 대장내시경 시나리오
- 현재 단계에 적용되는 제한사항 목록
- 음식·행동 이름 검색
- 제한 결과와 적용 기간
- 공식 출처와 확인일
- 질문으로 저장
- 보호자 개인 질문 목록
- 질문 완료·삭제
- 공식 매뉴얼 기반 제한사항 사전 등록
- 공식 출처·버전·확인일 표시
- 직원의 선택적 환자 추가 제한 등록·해제
- 직원 추가 제한 감사 기록

### 4.2 제외

- 섭취 또는 행동 허가 판정
- 환자 상태를 이용한 AI 의료판단
- 자유대화 의료 챗봇
- 질문의 실시간 직원 전송
- 직원 답변 채팅
- 직원의 공식 매뉴얼 수정·게시
- 실제 식이 처방·EMR·검사 예약 연동
- 모든 질환·수술·검사의 콘텐츠 구축
- 공식 자료 전문 복제
- 환자별 투약 지시 생성

## 5. 데모 시나리오

### 5.1 위암 위절제 수술

- 기존 가상 환자 김정우의 보호자 여정을 사용한다.
- 기존 여정은 수술 준비 단계에서 시작하며 식이 제한 데모는 발표자 도구로 회복실 단계까지 진행한 뒤 시연한다.
- 병원에서 식사 단계가 확인되기 전에는 물과 외부 음식 제공을 중단하도록 표시한다.
- 현재 단계와 무관하게 일반적인 수술 후 식사요법을 허가 정보로 사용하지 않는다.

검색 예시:

| 검색어 | 결과 | 이유 |
|---|---|---|
| 탄산음료 | 지금은 제공하지 마세요 | 위절제 후 가스와 불편감 관련 공식 제한 |
| 아이스크림 | 확인 전에는 제공하지 마세요 | 고당류 과다섭취 주의는 확인되나 현재 환자 허용 여부는 미확인 |
| 외부 미음 | 확인 전에는 제공하지 마세요 | 병원 식이 처방·제공 식사와 동일한지 확인 불가 |
| 커피 | 확인 전에는 제공하지 마세요 | 선택한 공식 자료에서 환자별 허용 근거를 확인하지 못함 |

### 5.2 오전 대장내시경

- 발표용 두 번째 가상 여정을 사용한다.
- 검사 예정 시각은 오전 9시로 고정한다.
- 기본 화면은 검사 3일 전 단계다.
- 발표자 도구에서 `검사 3일 전`, `검사 전날`, `절대 금식` 단계로 전환한다.
- 삼성서울병원 오전 대장내시경 공개 안내의 상대 시점과 제한 항목을 재구성한다.

검사 3일 전 제한 예시:

- 잡곡밥, 검은쌀, 현미밥, 깨죽
- 김치, 나물, 해조류, 버섯, 콩나물
- 씨 있는 과일
- 고추씨, 옥수수
- 견과류

검사 전날 제한 예시:

- 오후 7시 이후 일반 식사
- 자정 이후 음식과 물

절대 금식 단계 제한 예시:

- 물
- 약
- 껌
- 은단
- 담배

혈압약과 같은 예외는 앱이 복용 허가를 제공하지 않고 `예약 안내와 의료진 지시를 확인하세요`로 표시한다.

## 6. 정보 구조

```text
보호자 홈
├─ 현재 제한사항
│  ├─ 음식
│  ├─ 행동
│  └─ 준비사항
├─ 음식·행동 검색
│  └─ 제한 결과
│     ├─ 근거
│     ├─ 적용 단계·기간
│     ├─ 공식 출처
│     └─ 질문으로 저장
└─ 질문 목록
   ├─ 상담할 질문
   └─ 확인 완료

직원 운영 웹
└─ 적용 안내 확인
   ├─ 공식 매뉴얼·출처
   ├─ 현재 환자 적용 단계
   ├─ 선택적 추가 제한
   └─ 공식 안내 갱신 필요 신고
```

## 7. 아키텍처

```text
진료 일정·현재 단계
        ↓
Care Context Resolver
        ↓
Official Manual Guidance
        ↓
Optional Staff Supplement
        ↓
Restriction Resolver
├─ 현재 제한 목록
├─ 검색 결과
└─ 확인 필요 결과
        ↓
보호자 화면
├─ 제한사항
└─ 개인 질문 목록
```

### 7.1 Care Context Resolver

- 환자의 진료 항목과 현재 단계를 결정한다.
- 프로토타입에서는 가상 여정과 발표자 단계 전환을 사용한다.
- 실서비스에서는 병원 검사 예약, 수술 이벤트와 식이 처방을 원본으로 사용한다.
- 현재 단계를 확정하지 못하면 가장 보수적인 제한을 계산하지 않고 `현재 단계 확인 필요`를 반환한다.

### 7.2 Official Manual Guidance

- 공식 매뉴얼에서 사전에 구조화한 수술·검사 제한사항 묶음이다.
- 진료 항목의 세부 유형을 구분한다.
- 출처 URL, 확인일과 데이터 버전을 가진다.
- 프로토타입에서는 코드에 포함된 시드 데이터로 제공한다.
- 직원 화면에서 내용을 수정하거나 게시하지 않는다.
- 실서비스에서는 병원이 제공하는 승인 데이터 또는 별도 검수된 콘텐츠 배포 절차로 갱신한다.

### 7.3 Restriction Resolver

- 현재 단계에 적용되는 활성 공식 규칙만 조회한다.
- 음식·행동 검색어를 별칭과 함께 정규화한다.
- 명시적 제한이 있으면 `DO_NOT_PROVIDE`를 반환한다.
- 명시적 제한이 없거나 조건을 확정할 수 없으면 `CHECK_BEFORE_PROVIDING`을 반환한다.
- 직원 추가 제한이 있으면 공식 매뉴얼 결과보다 먼저 적용한다.
- 직원 추가 제한은 결과를 더 엄격하게 만들 수 있지만 제한을 해제하거나 허가할 수 없다.
- 허가 결과를 반환하지 않는다.

### 7.4 Question Notebook

- 보호자가 검색 결과를 질문으로 저장한다.
- 직원에게 자동 전송하지 않는다.
- 검색어와 자동 생성 질문만 저장하며 자유서술 의료정보를 받지 않는다.
- 보호자는 상담 후 `확인 완료`로 표시하거나 삭제할 수 있다.
- 답변 내용은 기록하지 않는다.

### 7.5 전체 수술·검사 확장

- `CareItem`, `CarePhase`, `RestrictionProtocol`은 특정 수술이나 검사명을 코드에 고정하지 않는다.
- 새 수술·검사는 검수된 공식 매뉴얼 데이터를 배포해 추가한다.
- 플랫폼은 모든 수술·검사를 등록할 수 있지만 공식 안내 데이터가 있는 항목만 사용자에게 안내한다.
- 콘텐츠가 없는 항목은 일반화하거나 유사 항목의 규칙을 재사용하지 않는다.
- 실제 병원 전체 적용 시 병원 항목 코드와 세부 프로토콜을 일대일로 매핑한다.

## 8. 데이터 모델

### 8.1 CareItem

| 필드 | 설명 |
|---|---|
| `id` | UUID |
| `type` | `SURGERY`, `EXAM`, `TREATMENT` |
| `name` | 사용자·직원 표시명 |
| `variant` | 조영제, 진정, 절제 범위 등 세부 유형 |
| `department` | 관리 부서 |
| `externalCode` | 선택적 병원 코드 |

프로토타입 기본 항목:

- `위암 위절제 수술`
- `오전 대장내시경`

### 8.2 CarePhase

| 필드 | 설명 |
|---|---|
| `id` | UUID |
| `careItemId` | 진료 항목 |
| `code` | 단계 코드 |
| `name` | 사용자 표시명 |
| `startsAtOffsetMinutes` | 예정 시각 기준 시작 오프셋 또는 `null` |
| `endsAtOffsetMinutes` | 예정 시각 기준 종료 오프셋 또는 `null` |
| `sequence` | 단계 순서 |

위암 수술 단계는 병원 이벤트 기반이며 대장내시경 단계는 검사 예정 시각의 상대 시간 기반이다.

### 8.3 RestrictionProtocol

| 필드 | 설명 |
|---|---|
| `id` | UUID |
| `careItemId` | 대상 수술·검사 |
| `version` | 1부터 증가하는 정수 |
| `status` | `ACTIVE`, `RETIRED` |
| `title` | 공식 안내 제목 |
| `sourceUrl` | 공식 출처 |
| `sourceTitle` | 출처 제목 |
| `sourceCheckedAt` | 출처 확인일 |
| `dataVersion` | 구조화 데이터 버전 |
| `activatedAt` | 데이터 적용 시각 |

공식 출처와 확인일이 없는 프로토콜은 활성화할 수 없다.

### 8.4 RestrictionRule

| 필드 | 설명 |
|---|---|
| `id` | UUID |
| `protocolId` | 프로토콜 |
| `phaseId` | 적용 단계 |
| `category` | `FOOD`, `MEDICATION`, `ACTIVITY`, `PREPARATION` |
| `itemName` | 대표 검색어 |
| `aliases` | 검색 별칭 |
| `resultType` | `DO_NOT_PROVIDE`, `CHECK_BEFORE_PROVIDING` |
| `headline` | 사용자 결과 제목 |
| `reason` | 쉬운 제한 이유 |
| `effectiveText` | 적용 기간 설명 |
| `fallbackQuestion` | 자동 생성 질문 |
| `sequence` | 목록 순서 |

`resultType`에 허가 상태를 추가하지 않는다.

### 8.5 StaffRestrictionSupplement

| 필드 | 설명 |
|---|---|
| `id` | UUID |
| `journeyId` | 적용할 가상 환자 여정 |
| `category` | `FOOD`, `MEDICATION`, `ACTIVITY`, `PREPARATION` |
| `itemName` | 추가 제한 대상 |
| `resultType` | `DO_NOT_PROVIDE`, `CHECK_BEFORE_PROVIDING` |
| `reason` | 직원이 선택한 사유 |
| `effectiveUntil` | 적용 종료 시각 |
| `createdBy` | 데모 직원 표시명 |
| `createdAt` | 생성 시각 |
| `status` | `ACTIVE`, `REVOKED`, `EXPIRED` |

- 공식 매뉴얼 규칙을 삭제하거나 완화하지 않는다.
- 결과 유형에 허가 상태를 제공하지 않는다.
- 사유는 `환자별 지시 확인`, `현재 단계 확인 필요`, `추가 제한 전달받음` 중 선택한다.
- 자유서술 의료지침을 입력하지 않는다.
- 해제는 기록을 삭제하지 않고 `REVOKED`로 변경한다.

### 8.6 SavedQuestion

| 필드 | 설명 |
|---|---|
| `id` | UUID |
| `journeyId` | 보호자 여정 |
| `query` | 사용자가 검색한 음식·행동 |
| `questionText` | 자동 생성 질문 |
| `reason` | 질문으로 저장된 이유 |
| `status` | `OPEN`, `DONE` |
| `createdAt` | 생성 시각 |
| `completedAt` | 확인 완료 시각 또는 `null` |

같은 여정에서 같은 정규화 검색어의 열린 질문은 중복 저장하지 않는다.

## 9. 사용자 화면

### 9.1 보호자 홈 제한 카드

현재 치료 단계 아래, 보호자 업무 위에 표시한다.

```text
현재 주의사항

수술 후 식사 안내가 확인되기 전까지
물과 외부 음식을 제공하지 마세요.

제한 3개 · 확인 필요 2개
[지금 피해야 할 것 보기]
```

대장내시경 시나리오:

```text
검사 3일 전

잡곡, 해조류, 씨 있는 과일과
견과류를 섭취하지 마세요.

다음 단계: 검사 전날 오후 7시
[전체 준비 일정]
```

### 9.2 제한사항 목록

- 현재 단계
- 제한 시작·종료 조건
- 음식, 약, 행동, 준비사항 탭
- 대표 제한 항목
- `다른 음식·행동 검색`
- 공식 출처

`가능한 음식` 목록은 제공하지 않는다.

### 9.3 검색

입력 예:

- 탄산음료
- 아이스크림
- 커피
- 딸기
- 김
- 물

최근 검색과 자동완성은 현재 활성 공식 안내의 대표 검색어·별칭만 사용한다. 의료 용어나 결과를 생성하지 않는다.

### 9.4 검색 결과: 명시적 제한

```text
지금은 제공하지 마세요

딸기

씨가 있는 과일은 대장내시경 검사
3일 전부터 제한하도록 안내되어 있습니다.

적용 기간
검사 3일 전부터 검사 종료 전까지

[질문으로 저장]
[공식 안내 원문 보기]
```

### 9.5 검색 결과: 확인 필요

```text
확인 전에는 제공하지 마세요

커피

현재 적용 중인 병원 승인 안내만으로
섭취 여부를 확인할 수 없습니다.

앱은 섭취를 허가하지 않습니다.

[의료진에게 물어볼 질문으로 저장]
```

### 9.6 질문 목록

```text
의료진에게 확인할 질문 2개

□ 커피를 마셔도 되는지 확인
  이유: 현재 안내에서 확인되지 않음

□ 복용 중인 혈압약의 시간을 확인
  이유: 환자별 복약 지시 필요

[상담할 때 크게 보기]
```

- 질문은 생성 시각순으로 표시한다.
- `확인 완료`는 질문을 완료 영역으로 이동한다.
- 실제 답변을 입력하거나 공유하지 않는다.
- 빈 상태에서는 현재 제한사항으로 돌아가는 행동을 제공한다.

## 10. 직원 화면

기존 직원 콘솔에 `적용 안내 확인` 메뉴를 추가한다. 공식 매뉴얼은 읽기 전용이며 직원 입력은 특정 환자에게 추가 제한이 필요한 경우에만 선택적으로 사용한다.

### 10.1 공식 안내 확인

- 현재 환자의 수술·검사와 단계
- 적용 중인 공식 제한
- 공식 출처
- 출처 확인일
- 데이터 버전
- `갱신 필요 신고`

### 10.2 선택적 추가 제한

- 제한 카테고리
- 제한 대상 음식·행동
- 결과 유형
- 제한 사유
- 적용 종료 시각
- 환자 화면 미리보기
- 추가 제한 적용

추가 제한은 공식 안내보다 엄격한 방향으로만 적용한다. 직원은 공식 제한을 삭제하거나 음식·행동을 허가할 수 없다.

### 10.3 추가 제한 해제

- 활성 추가 제한 목록
- 적용자와 적용 시각
- 종료 예정 시각
- `추가 제한 해제`

해제 사유는 `기간 종료`, `잘못 등록`, `새 지시로 대체` 중 선택하며 감사 기록에 남긴다.

## 11. API 설계

| Method | Path | 목적 |
|---|---|---|
| `GET` | `/caregiver-journeys/demo/restrictions` | 현재 제한 목록 |
| `GET` | `/caregiver-journeys/demo/restrictions/search?q=` | 음식·행동 검색 |
| `GET` | `/caregiver-journeys/demo/questions` | 개인 질문 목록 |
| `POST` | `/caregiver-journeys/demo/questions` | 검색 결과를 질문으로 저장 |
| `POST` | `/caregiver-journeys/demo/questions/:id/complete` | 질문 확인 완료 |
| `DELETE` | `/caregiver-journeys/demo/questions/:id` | 질문 삭제 |
| `GET` | `/staff/demo/restriction-guidance` | 적용 공식 안내와 추가 제한 조회 |
| `POST` | `/staff/demo/restriction-supplements` | 선택적 추가 제한 등록 |
| `POST` | `/staff/demo/restriction-supplements/:id/revoke` | 추가 제한 해제 |
| `POST` | `/staff/demo/restriction-guidance/report` | 공식 안내 갱신 필요 신고 |
| `POST` | `/demo/scenarios/:scenarioId/select` | 발표 시나리오 선택 |
| `POST` | `/demo/scenarios/:scenarioId/advance` | 단계 전환 |

모든 응답은 공유 Zod 스키마로 검증한다. 현재 데모 구조와 일관되게 변경 후 서버 응답을 화면 상태의 원본으로 사용한다.

## 12. 오류와 복구

### 현재 단계 없음

- 제한사항을 계산하지 않는다.
- `현재 치료 단계를 확인할 수 없습니다`를 표시한다.
- 음식과 행동을 제공하지 말고 병원 안내를 확인하도록 한다.

### 공식 안내 데이터 없음

- `등록된 병원 승인 안내가 없습니다`를 표시한다.
- 검색 결과는 `확인 전에는 제공하지 마세요`로 반환한다.
- 질문 저장 행동을 제공한다.

### 검색 결과 없음

- AI로 답을 생성하지 않는다.
- `확인 전에는 제공하지 마세요`를 반환한다.
- 검색어로 질문을 자동 생성한다.

### 출처 만료

- 프로토타입에서는 출처 확인 후 365일이 지나면 `갱신 필요`를 표시한다.
- `갱신 필요`만으로 활성 공식 안내를 자동 종료하지 않는다.
- 실서비스의 만료 정책은 병원 콘텐츠 책임자가 결정한다.

### 질문 저장 실패

- 검색 결과를 유지한다.
- 재시도 행동을 제공한다.
- 저장 성공 전 질문 개수를 변경하지 않는다.

### 직원 추가 제한 실패

- 보호자 화면에 반영하지 않는다.
- 입력값을 유지하고 재시도를 제공한다.
- 공식 안내는 그대로 유지한다.

## 13. 개인정보·의료 안전

- 실제 환자정보와 식이 처방을 사용하지 않는다.
- 환자별 허용·금지 판단을 생성하지 않는다.
- 병원에서 제공된 식사와 의료진 지시를 항상 우선한다.
- 복약 질문에 복용 지시를 생성하지 않는다.
- 공식자료는 짧게 재구성하고 원문 링크를 제공한다.
- 실제 서비스에서는 삼성서울병원 콘텐츠 사용 승인을 받아야 한다.
- 질문 목록은 직원에게 자동 전송하지 않는다.
- 자유서술 답변을 저장하지 않는다.
- 모든 직원 추가 제한 등록과 해제에 감사 기록을 남긴다.

## 14. 테스트 전략

### 도메인 단위 테스트

- 현재 단계에 적용되는 규칙만 반환한다.
- 명시적 규칙은 `DO_NOT_PROVIDE`를 반환한다.
- 규칙이 없으면 `CHECK_BEFORE_PROVIDING`을 반환한다.
- 어떤 입력에도 허가 결과를 반환하지 않는다.
- 별칭 검색이 대표 규칙을 찾는다.
- 같은 열린 질문을 중복 저장하지 않는다.
- 출처 없는 공식 안내 데이터를 활성화하지 않는다.
- 직원 추가 제한이 공식 규칙을 완화하지 못한다.
- 직원 추가 제한에 허가 결과를 저장하지 못한다.
- 만료된 직원 추가 제한을 적용하지 않는다.

### API 통합 테스트

- 위암 수술 시나리오에서 탄산음료 제한을 반환한다.
- 위암 수술 시나리오에서 커피를 확인 필요로 반환한다.
- 대장내시경 3일 전 딸기·김·견과류 제한을 반환한다.
- 대장내시경 절대 금식 단계에서 물 제한을 반환한다.
- 질문 저장·완료·삭제가 서버 상태에 반영된다.
- 시나리오 전환 후 다른 프로토콜을 사용한다.
- 직원 추가 제한이 공식 안내와 함께 보호자 화면에 반영된다.
- 직원 추가 제한 해제 후 공식 안내만 유지된다.

### 웹 컴포넌트 테스트

- 홈에서 현재 제한 카드가 보인다.
- 제한과 확인 필요를 색상 외 텍스트로 구분한다.
- 결과에 적용 단계와 출처가 보인다.
- 검색 결과가 허가 표현을 사용하지 않는다.
- 질문 목록이 상담용 큰 글씨 화면을 제공한다.
- 직원 화면이 공식 출처를 읽기 전용으로 표시한다.
- 선택적 추가 제한 등록과 해제 상태를 표시한다.

### 발표 E2E

1. 위암 수술 회복실 단계에서 외부 음식 제한을 확인한다.
2. 탄산음료를 검색해 명시적 제한과 출처를 확인한다.
3. 커피를 검색해 확인 필요 결과를 질문으로 저장한다.
4. 질문 목록에서 상담용 화면을 확인한다.
5. 발표자 도구로 대장내시경 시나리오를 선택한다.
6. 검사 3일 전 제한 목록과 딸기 검색 결과를 확인한다.
7. 절대 금식 단계로 전환해 물 제한을 확인한다.
8. 직원 화면에서 공식 출처를 확인하고 선택적 추가 제한을 등록한다.
9. 보호자 화면에 추가 제한이 반영되는 것을 확인한다.

## 15. 24시간 구현 우선순위

### 필수

- 두 데모 시나리오
- 활성 공식 안내와 제한 규칙 메모리 데이터
- 현재 제한 목록
- 검색과 두 결과 유형
- 질문 저장·완료·삭제
- 직원의 공식 안내 읽기 전용 조회
- 직원의 선택적 추가 제한 등록·해제
- 공개자료 출처 표시

### 시간 여유가 있을 때

- 별칭 자동완성
- 출처 갱신 필요 표시
- 질문 상담용 큰 글씨 화면

직원 이벤트 자동 수신·예외 처리 기능을 먼저 완성하고, 이 기능은 같은 서버 상태와 감사 기록을 재사용한다.

## 16. 완료 기준

- 위암 수술과 대장내시경 시나리오를 전환할 수 있다.
- 현재 단계에 맞는 제한사항만 표시한다.
- 음식·행동 검색이 명시적 제한 또는 확인 필요만 반환한다.
- 앱 어디에도 음식·행동 허가 결과가 없다.
- 검색 결과를 개인 질문으로 정리할 수 있다.
- 질문은 직원에게 자동 전송되지 않는다.
- 직원 화면에서 적용 중인 공식 출처와 데이터 버전을 확인할 수 있다.
- 직원은 공식 안내를 수정하거나 완화할 수 없다.
- 선택적 추가 제한과 해제 이력이 남는다.
- 두 시나리오의 발표 E2E가 통과한다.
- 모바일 390×844와 데스크톱 1280×900에서 주요 흐름을 완료한다.
