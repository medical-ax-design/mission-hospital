# Wait:ON 병원 전산 이벤트·직원 운영 워크플로 설계

## 1. 문서 목적

이 문서는 기존 보호자 동행 프로토타입에 다음 기능을 추가하기 위한 승인 설계다.

- 병원 전산 이벤트 자동 수신 시뮬레이션
- 간호사의 예외 이벤트 승인·보류
- 원무직원의 보호자 업무·준비물·장소 안내 관리
- 승인된 정보의 보호자 화면 반영

24시간 발표용 프로토타입을 대상으로 하며 실제 HIS, EMR, OCS, 문자·알림톡 시스템과 연동하지 않는다.

## 2. 제품 결정

Wait:ON은 병원 전산이나 문자 알림 시스템을 대체하지 않는다. 기존 병원 시스템에서 발생하는 치료 진행 이벤트를 받아 보호자가 이해할 수 있는 표현과 다음 행동으로 변환하는 보호자 경험 계층이다.

실서비스의 기본 원칙은 다음과 같다.

- 환자 기본정보, 수술 오더와 실제 수행 기록은 기존 병원 시스템이 원본이다.
- 정상 치료 진행 상태를 Wait:ON에 다시 입력하지 않는다.
- 간호사는 보호자 공개 여부와 예외만 처리한다.
- 원무직원은 행정업무, 필요 서류, 처리 장소와 이동 순서를 관리한다.
- 보호자는 승인된 치료 상태와 행정 안내만 조회한다.
- 문자는 짧은 상태와 Wait:ON 진입 링크를 전달하는 보조 채널이다.

## 3. 프로토타입 목표

발표에서 다음 폐쇄 루프를 중단 없이 시연한다.

```text
가상 병원 전산 이벤트 발생
→ 내부 상태를 보호자용 표현으로 자동 변환
→ 정상 이벤트는 자동 공개
→ 순서 이상·확인 필요 이벤트만 간호사가 승인 또는 보류
→ 원무직원이 보호자 행정업무 게시
→ 보호자 화면에 상태와 다음 행동 반영
→ 변경 이력 확인
```

성공 기준은 화면 수가 아니라 역할 사이에서 데이터가 정확하게 이동하고, 가상 데이터와 공개자료 기반 안내가 구분되는 것이다.

## 4. 범위

### 4.1 포함

- 발표자 전용 가상 병원 이벤트 발생
- 수신 이벤트 목록과 상세
- 가상 내부 코드의 보호자용 문구 매핑
- 정상 이벤트 자동 공개
- 간호사 예외 이벤트 승인
- 간호사 예외 이벤트 보류와 보류 사유
- 원무직원 보호자 업무 작성·수정·게시
- 업무명, 필요 서류, 처리 장소, 번호표 규칙, 순서, 대체 안내
- 공개자료 출처 URL, 확인일, 수정자
- 보호자 홈의 상태·업무 반영
- 변경 이력
- 데모 초기화
- 모바일·데스크톱 반응형 화면

### 4.2 제외

- 실제 환자정보
- 실제 직원 로그인과 병원 SSO
- 실제 HIS, EMR, OCS, 수술실 시스템 연동
- 실제 문자, 알림톡, 앱 푸시 전송
- 성인 보호자 동의·권한 인증
- 실제 삼성서울병원 내부 상태코드
- 실제 실내지도, 보행시간, 키오스크 번호, 혼잡도
- 진단, 의료지침, 정상 여부, 예상 종료시간 생성
- 실제 Voice EMR 또는 진료기록 요약
- PostgreSQL 영속화와 운영 배포

## 5. 역할과 책임

| 역할 | 책임 | 허용 행동 | 금지 행동 |
|---|---|---|---|
| 발표자 | 병원 전산 연동 시연 | 가상 이벤트 발생, 데모 초기화 | 실제 데이터 입력 |
| 간호사 | 예외 이벤트의 보호자 공개 안전 확인 | 확인 필요 이벤트 승인, 보류, 보류 사유 입력 | 정상 이벤트 재입력, 수술 원본 기록 수정, 의료 판단 생성 |
| 원무직원 | 보호자 행정업무 관리 | 업무·서류·장소·순서 작성 및 게시 | 임상 상태 변경 |
| 보호자 | 승인된 정보 확인 | 현재 상태, 지금 할 일, 장소·준비물 확인 | 병원 원본 데이터 수정 |

프로토타입에서는 역할 전환 메뉴로 각 화면에 진입한다. 실제 인증을 구현하지 않으며 화면에 `발표용 역할 전환`이라고 표시한다.

## 6. 아키텍처

```text
┌──────────────────────────────────────────────┐
│ 실제 환경의 병원 시스템                      │
│ HIS·EMR │ 수술실 시스템 │ 원무·수납 │ 알림 시스템 │
└──────────────────────┬───────────────────────┘
                       │ 상태 이벤트
┌──────────────────────▼───────────────────────┐
│ Wait:ON 서버                                 │
│ 연동 어댑터 → 상태 변환기 → 공개 워크플로     │
│                  ↘ 업무·가이드 ↗              │
│              권한 경계·감사 기록              │
└──────────────┬───────────────┬───────────────┘
               │               │
       ┌───────▼──────┐  ┌────▼──────────────┐
       │ 직원 운영 웹  │  │ 보호자 모바일 웹   │
       │ 간호사·원무   │  │ 상태·업무·이동안내 │
       └──────────────┘  └───────────────────┘
```

프로토타입에서는 병원 시스템 대신 `DemoHospitalEventAdapter`가 가상 이벤트를 생성한다. 애플리케이션 서비스는 어댑터 인터페이스만 의존하므로 향후 실제 연동 어댑터로 교체할 수 있다.

### 6.1 모듈 경계

#### Hospital Event Ingestion

- 외부 또는 데모 이벤트를 수신한다.
- 이벤트 식별자 중복을 거부한다.
- 수신 시각과 원본 발생 시각을 구분해 기록한다.
- 이벤트 내용을 보호자 화면에 직접 노출하지 않는다.

#### Caregiver Status Mapping

- 내부 이벤트 종류를 보호자용 상태와 문구로 변환한다.
- 매핑되지 않은 이벤트는 공개 대기열에 넣지 않고 `UNMAPPED`로 남긴다.
- 정상 여부나 예상시간을 추론하지 않는다.

#### Staff Review

- 정상 순서로 들어온 매핑 가능 이벤트는 자동 공개한다.
- `requiresReview`가 지정됐거나 이전 단계로 역행하는 이벤트는 `NEEDS_REVIEW`로 분류한다.
- 간호사는 `NEEDS_REVIEW` 이벤트만 승인하거나 보류한다.
- 자동 공개 또는 간호사 승인된 이벤트만 보호자 여정의 현재 상태를 변경한다.

#### Administrative Guidance

- 원무직원이 보호자 업무와 공개 안내를 관리한다.
- 초안과 게시 상태를 분리한다.
- 게시된 내용만 보호자에게 제공한다.
- 안내 출처와 확인일을 필수로 기록한다.

#### Caregiver Journey

- 승인된 최신 치료 상태와 현재 활성 행정업무를 결합한다.
- 기존 보호자 홈, 치료 진행, 업무, 이동 가이드 화면에 동일한 서버 상태를 제공한다.

#### Audit

- 이벤트 수신, 승인, 보류, 안내 게시, 데모 초기화를 기록한다.
- 감사 기록은 수정하지 않는다.

## 7. 데이터 모델

프로토타입은 메모리 저장소를 사용하지만 엔터티와 식별자는 운영 구조를 고려해 분리한다.

### 7.1 HospitalEvent

| 필드 | 설명 |
|---|---|
| `id` | Wait:ON 이벤트 UUID |
| `externalEventId` | 가상 병원 시스템 이벤트 식별자 |
| `journeyId` | 보호자 여정 식별자 |
| `eventType` | 가상 내부 이벤트 종류 |
| `requiresReview` | 발표용으로 예외 검토를 강제할지 여부 |
| `occurredAt` | 원본 시스템 발생 시각 |
| `receivedAt` | Wait:ON 수신 시각 |
| `reviewPolicy` | `AUTO_PUBLISH` 또는 `REVIEW_REQUIRED` |
| `reviewStatus` | `AUTO_PUBLISHED`, `NEEDS_REVIEW`, `APPROVED`, `HELD`, `UNMAPPED` |
| `mappedStage` | 보호자용 단계 또는 `null` |
| `mappedMessage` | 보호자 공개 후보 문구 또는 `null` |
| `reviewedBy` | 검토자 표시명 또는 `null` |
| `reviewedAt` | 검토 시각 또는 `null` |
| `holdReason` | 보류 사유 또는 `null` |

지원하는 가상 이벤트는 다음 네 개로 제한한다.

| `eventType` | 보호자 단계 | 보호자 공개 후보 문구 |
|---|---|---|
| `OR_ADMITTED` | `IN_OPERATING_ROOM` | 수술실에 입실했습니다 |
| `OP_IN_PROGRESS` | `IN_PROGRESS` | 수술이 진행 중입니다 |
| `PACU_ADMITTED` | `RECOVERY` | 회복실에서 상태를 확인하고 있습니다 |
| `WARD_RETURNED` | `COMPLETED` | 병실로 이동했습니다 |

이 코드는 발표용이며 삼성서울병원의 실제 내부 코드가 아니다.

### 7.2 AdministrativeTask

| 필드 | 설명 |
|---|---|
| `id` | 업무 UUID |
| `journeyId` | 보호자 여정 식별자 |
| `title` | 보호자에게 보이는 업무명 |
| `description` | 쉬운 설명 |
| `activationStage` | 업무가 활성화되는 보호자 단계 |
| `destinationName` | 공개자료로 확인한 처리 장소 |
| `requiredItems` | 준비서류·준비물 목록 |
| `ticketRule` | 번호표 규칙. 확인되지 않으면 `확인 필요` |
| `steps` | 처리 순서 |
| `fallbackText` | 처리 불가 시 대안 |
| `sourceUrl` | 공식 공개자료 URL |
| `sourceCheckedAt` | 공개자료 확인일 |
| `status` | `DRAFT`, `PUBLISHED` |
| `updatedBy` | 마지막 수정자 |
| `updatedAt` | 마지막 수정 시각 |

업무 변경 이력을 보존하기 위해 다음 버전 필드를 함께 둔다.

| 필드 | 설명 |
|---|---|
| `logicalTaskId` | 같은 업무의 버전을 묶는 식별자 |
| `version` | 1부터 증가하는 정수 |
| `replacesId` | 직전 게시본 식별자 또는 `null` |

현재 데모의 `본관 1층 3번 키오스크`, `도보 6분`, `번호표 불필요`, `보호자 신분증만 필요` 정보는 제거한다. 공개자료에 근거한 다음 안내를 기본 예시로 사용한다.

- 업무: 의무기록 사본 발급 준비
- 장소: 암병원 1층 의무기록 사본 관련 창구
- 준비 항목: 신청자 신분증, 환자 동의서, 가족관계 확인서류가 필요할 수 있음
- 안내: 방문 전 신청 유형별 구비서류 확인
- 출처: [삼성서울병원 의무기록 사본 발급 안내](https://www.samsunghospital.com/home/reservation/certificate.do)

### 7.3 AuditEntry

| 필드 | 설명 |
|---|---|
| `id` | 감사 기록 UUID |
| `journeyId` | 관련 여정 |
| `actorRole` | `SYSTEM`, `PRESENTER`, `NURSE`, `ADMIN_STAFF` |
| `actorName` | 행위자 표시명 |

## 8. 상태 규칙

### 8.1 이벤트 검토

```text
수신
├─ 매핑 가능 + 정상 순서 + AUTO_PUBLISH
│  └─ AUTO_PUBLISHED → 보호자 상태 변경
├─ requiresReview 또는 단계 순서 확인 필요
│  └─ NEEDS_REVIEW
│     ├─ 간호사 승인 → APPROVED → 보호자 상태 변경
│     └─ 간호사 보류 → HELD → 보호자 상태 유지
└─ 매핑 불가 → UNMAPPED → 보호자 미공개
```

### 8.2 단계 순서

```text
PREPARING
→ IN_OPERATING_ROOM
→ IN_PROGRESS
→ RECOVERY
→ COMPLETED
```

- 동일 단계 이벤트의 자동 공개와 승인은 멱등적으로 처리한다.
- 이미 공개된 단계보다 이전 단계의 이벤트는 `NEEDS_REVIEW` 상태로 유지하고 `순서 확인 필요`를 표시한다.
- `HELD` 이벤트는 자동 재처리하지 않는다.
- 보류 이벤트를 공개하려면 간호사가 `보류 해제 후 공개 승인` 행동을 명시적으로 수행한다.
- 보호자 화면의 `lastVerifiedAt`은 마지막 공개 이벤트에서 계산한다.
- 자동 공개는 `verifiedBy: 병원 전산`, 예외 승인 공개는 `verifiedBy: 간호사 확인`으로 표시한다.

### 8.3 행정업무

- `DRAFT`는 보호자에게 노출되지 않는다.
- `PUBLISHED`이며 현재 단계가 `activationStage` 이상인 업무만 활성화한다.
- 게시된 업무를 수정하면 같은 업무의 새 초안을 만들고 재게시한다.
- 프로토타입에서는 활성 업무를 하나로 제한한다.

## 9. 화면 설계

### 9.1 발표용 역할 선택

목적: 실제 인증이 아니라는 사실을 유지하면서 역할별 화면으로 이동한다.

필수 요소:

- `발표용 역할 전환` 라벨
- 보호자, 간호사, 원무직원 선택
- 발표자 도구 진입
- 모든 데이터가 가상임을 알리는 고정 문구

### 9.2 간호사 이벤트 콘솔

목적: 정상 상태를 다시 입력하지 않고 자동 수신된 최근 이벤트와 검토가 필요한 예외를 확인한다.

필수 요소:

- 자동 공개된 최근 이벤트
- 검토 필요 이벤트 수
- 이벤트 종류, 가상 환자 표시명, 발생·수신 시각
- 자동 매핑된 보호자 단계와 공개 후보 문구
- 현재 보호자 공개 단계
- 예외 이벤트의 `공개 승인`
- 예외 이벤트의 `알림 보류`
- 보류 사유 선택

보류 사유는 자유서술 대신 다음 값으로 제한한다.

- 환자 확인 필요
- 단계 순서 확인 필요
- 보호자 공개 보류
- 잘못 수신된 이벤트

정상 이벤트에는 승인 버튼을 표시하지 않는다. 예외 승인 후 서버가 반환한 여정을 화면 상태의 원본으로 사용한다.

### 9.3 원무직원 안내 콘솔

목적: 공개자료를 바탕으로 보호자 행정업무와 처리 방법을 게시한다.

필수 입력:

- 업무명
- 쉬운 설명
- 활성 단계
- 처리 장소
- 준비물 목록
- 번호표 규칙
- 처리 순서
- 실패 시 대안
- 공식 출처 URL
- 출처 확인일

필수 행동:

- 초안 저장
- 보호자 화면 미리보기
- 게시

검증 규칙:

- 공식 출처 URL과 확인일이 없으면 게시할 수 없다.
- 근거 없는 키오스크 번호와 이동시간을 입력하지 않는다.
- 번호표 여부를 확인하지 못했으면 `현장 안내 확인 필요`를 선택한다.
- 의료지침이나 환자별 판단을 입력하지 않는다.

### 9.4 보호자 홈

읽기 순서:

1. 가상 환자와 치료명
2. 병원이 확인한 현재 단계
3. 마지막 확인 시각과 확인 역할
4. 다음 알림 조건
5. 지금 할 보호자 업무
6. 준비물과 처리 장소

보호자 공개 문구에는 다음을 표시하지 않는다.

- 수술이 정상이라는 판단
- 회복이 정상이라는 판단
- 예상 종료·각성·병실 복귀 시각
- 내부 이벤트 코드
- 확인되지 않은 상세 경로

### 9.5 발표자 이벤트 도구

목적: 실제 HIS 연동을 대신해 이벤트 기반 구조를 시연한다.

필수 요소:

- 다음 가상 이벤트 종류
- 이벤트 발생 버튼
- 현재 이벤트 수신·검토·공개 상태
- 전체 데모 초기화

일반 사용자 URL에는 노출하지 않고 `?demo=1`에서만 제공한다.

### 9.6 감사 기록

목적: 누가 어떤 정보를 공개하거나 보류했는지 발표에서 확인한다.

표시 항목:

- 시각
- 역할과 표시명
- 행동
- 대상
- 결과

### 9.7 화면 경로

| 경로 | 화면 |
|---|---|
| `/` | 기존 보호자 여정 |
| `/staff/nurse?demo=1` | 간호사 이벤트 콘솔 |
| `/staff/administration?demo=1` | 원무직원 안내 콘솔 |
| `/staff/audit?demo=1` | 감사 기록 |
| `/demo/control?demo=1` | 발표자 이벤트 도구와 초기화 |

직원·발표자 경로는 `demo=1`이 없으면 데모 전용 화면이라는 안내만 표시하고 기능을 제공하지 않는다.

## 10. API 설계

기존 `/caregiver-journeys/demo` 응답은 승인된 현재 상태와 활성 업무를 계속 제공한다.

| Method | Path | 역할 | 목적 |
|---|---|---|---|
| `GET` | `/staff/demo/events` | 간호사 | 이벤트 목록 조회 |
| `POST` | `/staff/demo/events/:eventId/approve` | 간호사 | 공개 승인 |
| `POST` | `/staff/demo/events/:eventId/hold` | 간호사 | 알림 보류 |
| `POST` | `/staff/demo/events/:eventId/release-and-approve` | 간호사 | 보류 해제 후 공개 승인 |
| `GET` | `/staff/demo/tasks` | 원무직원 | 업무 초안·게시본 조회 |
| `PUT` | `/staff/demo/tasks/:taskId/draft` | 원무직원 | 업무 초안 저장 |
| `POST` | `/staff/demo/tasks/:taskId/publish` | 원무직원 | 업무 게시 |
| `GET` | `/staff/demo/audit` | 직원 | 감사 기록 조회 |
| `POST` | `/demo/hospital-events` | 발표자 | 가상 이벤트 발생 |
| `POST` | `/demo/reset` | 발표자 | 데모 초기화 |

### 10.1 오류 응답

| 오류 | HTTP | 화면 처리 |
|---|---:|---|
| 이벤트 없음 | 404 | 목록을 재조회하고 이미 처리됐을 수 있음을 안내 |
| 자동 공개·승인된 이벤트 재승인 | 409 | 현재 공개 상태를 표시 |
| 단계 역행 | 409 | `단계 순서 확인 필요`로 유지 |
| 보류 사유 누락 | 400 | 보류 대화상자에서 사유 선택 요청 |
| 필수 출처 누락 | 400 | 누락 필드에 오류 표시 |
| 응답 계약 불일치 | 502 | 데이터를 화면 상태에 반영하지 않고 재시도 제공 |

## 11. 개인정보·안전

- 프로토타입은 가상 환자만 사용한다.
- 실제 성인 보호자 연결이 구현된 것처럼 표현하지 않는다.
- 실제 서비스에서는 환자 동의, 보호자 본인확인, 접근 유효기간과 철회가 선행돼야 한다.
- 최소 공개 원칙에 따라 치료 단계와 보호자 행동에 필요한 정보만 제공한다.
- 원본 이벤트 내용은 보호자에게 직접 노출하지 않는다.
- 모든 자동 공개와 직원 변경은 감사 기록을 남긴다.
- 의료적 판단과 시간 예측은 생성하지 않는다.
- 공개자료 안내에는 출처와 확인일을 표시한다.

## 12. 오류와 복구

### 이벤트 수신 실패

- 보호자 상태는 마지막 자동 공개 또는 승인 상태를 유지한다.
- 직원 화면에 `이벤트 수신을 확인할 수 없습니다`를 표시한다.
- 발표자 도구에서 같은 `externalEventId`로 재전송하면 중복 처리하지 않는다.

### 승인 요청 실패

- 화면에서 낙관적으로 상태를 변경하지 않는다.
- 버튼을 다시 활성화하고 재시도를 제공한다.
- 서버 성공 응답을 받은 뒤에만 목록과 보호자 여정을 갱신한다.

### 안내 게시 실패

- 작성 중인 입력값을 브라우저 상태에 유지한다.
- 누락된 출처나 필수 항목을 해당 필드 가까이에 표시한다.
- 게시 실패 시 기존 게시본은 그대로 유지한다.

### 데모 초기화

- 확인 대화상자를 거친다.
- 초기화 후 이벤트, 검토 상태, 업무, 감사 기록과 보호자 여정을 같은 초기 시점으로 되돌린다.

## 13. 테스트 전략

### 도메인 단위 테스트

- 내부 이벤트가 정확한 보호자 단계와 문구로 매핑된다.
- 매핑되지 않은 이벤트가 공개되지 않는다.
- 정상 이벤트가 자동 공개되어 여정 상태를 변경한다.
- `NEEDS_REVIEW` 이벤트는 승인 전 여정 상태를 변경하지 않는다.
- 승인 이벤트가 여정 상태를 변경한다.
- 보류 이벤트가 상태를 변경하지 않는다.
- 단계 역행이 거부된다.
- 중복 이벤트가 멱등적으로 처리된다.
- 초안 업무가 보호자에게 노출되지 않는다.
- 활성 단계 이전 업무가 노출되지 않는다.

### API 통합 테스트

- 가상 이벤트 발생부터 직원 목록 조회까지 검증한다.
- 정상 이벤트 자동 공개 후 `/caregiver-journeys/demo` 상태가 바뀐다.
- 예외 이벤트 승인 후 `/caregiver-journeys/demo` 상태가 바뀐다.
- 보류 후 보호자 상태가 유지된다.
- 원무 업무 게시 후 보호자 응답에 업무가 반영된다.
- 출처 없는 업무 게시를 거부한다.
- 데모 초기화가 전체 상태를 복원한다.

### 웹 컴포넌트 테스트

- 역할 전환과 가상 데이터 라벨을 확인한다.
- 간호사 승인·보류의 로딩, 성공, 실패 상태를 확인한다.
- 원무 입력 검증과 게시 미리보기를 확인한다.
- 보호자 화면이 승인된 상태와 게시된 업무만 표시한다.
- 색상 없이 상태를 구분할 수 있는지 확인한다.

### 발표 E2E

1. 보호자 화면에서 초기 `수술 준비 중`을 확인한다.
2. 발표자가 정상 `OR_ADMITTED` 이벤트를 발생시킨다.
3. 보호자 화면이 별도 재입력 없이 `수술실에 입실했습니다`로 바뀌는 것을 확인한다.
4. 간호사 화면에서 자동 공개 이력을 확인한다.
5. 발표자가 `requiresReview`가 지정된 `PACU_ADMITTED` 이벤트를 발생시킨다.
6. 간호사가 예외 이벤트를 공개 승인한다.
7. 원무직원이 공개자료 기반 업무를 게시한다.
8. 보호자 화면에서 회복실 상태, 준비물과 처리 장소를 확인한다.
9. 다른 예외 이벤트를 보류하고 보호자에게 공개되지 않는 것을 시연한다.
10. 감사 기록에서 자동 공개·승인·보류·게시 이력을 확인한다.

## 15. 완료 기준

- 가상 병원 이벤트가 간호사 화면에 자동으로 나타난다.
- 정상 이벤트는 직원 재입력 없이 보호자 상태를 변경한다.
- 예외 이벤트는 간호사가 승인한 경우에만 보호자 상태를 변경한다.
- 보류한 이벤트는 보호자에게 공개되지 않는다.
- 원무직원이 게시한 업무·준비물·장소가 보호자 화면에 반영된다.
- 출처가 없는 안내는 게시할 수 없다.
- 모든 자동 공개, 승인, 보류, 게시와 초기화에 감사 기록이 남는다.
- 화면에서 가상 내부 코드와 삼성서울병원 실제 코드를 혼동하지 않는다.
- 현재 데모의 근거 없는 키오스크 번호, 이동시간, 번호표 규칙과 준비물 단정이 제거된다.
- 서버와 웹의 단위·통합 테스트가 통과한다.
- TypeScript 검사와 프로덕션 빌드가 통과한다.
- 390×844와 1280×900에서 전체 발표 흐름을 완료한다.

## 17. 공개자료 기준

프로토타입 콘텐츠는 다음 삼성서울병원 공식 공개자료에서 확인할 수 있는 범위만 사용한다.

- [입원환자 모바일 앱 안내](https://www.samsunghospital.com/_newmweb/info/guide/web_app_guide_in.pdf): 수술·퇴원 일정 알림, 검사·시술·치료 일정, 완료 일정 표시
- [암병원 3층 안내](https://www.samsunghospital.com/_newhome/info/guide/cancer/3F.html): 수술실, 회복실, 수술환자 보호자 대기실
- [의무기록 사본 발급 안내](https://www.samsunghospital.com/home/reservation/certificate.do): 대리 신청 구비서류와 암병원 발급 장소
- [개인정보처리방침](https://www.samsunghospital.com/home/member/protect.do): EMR·OCS, 키오스크, 순번 시스템, 문자·알림톡 관련 개인정보 처리

공개자료로 확인할 수 없는 실제 내부 상태코드, 실시간 API, 성인 보호자 조회 권한, 키오스크 번호, 보행시간과 번호표 규칙은 데모에서 실제 사실처럼 표시하지 않는다.
