# Wait:ON 문서 정리 설계

## 1. 목적

현재 `docs` 최상위에는 개발 중인 보호자 동행 프로토타입과 이전
검사·수술 준비 오케스트레이션 서비스 문서가 함께 있다. 새 팀원이
현재 요구사항과 구현 상태를 잘못 해석하지 않도록 기준 문서와 과거
설계 자산을 분리한다.

## 2. 검토한 방식

### A. 아카이브 분리 — 선택

현재 기준 문서만 `docs` 최상위에 두고 이전 제품 트랙과 완료된 작업
계획은 `docs/archive`로 이동한다. Git 기록 외에도 의사결정 배경을
찾을 수 있으면서 현재 범위를 분명하게 유지할 수 있다.

### B. 완전 삭제

최상위 구조는 가장 단순하지만 이전 조사와 설계 근거를 재사용하기
어렵다. Git 기록을 직접 탐색해야 하므로 비개발 직군의 접근성도
낮아진다.

### C. 기존 위치 유지와 상태 배너 추가

파일 이동이 없다는 장점은 있지만 문서 수와 탐색 부담이 줄지 않는다.
잘못된 문서를 먼저 열 가능성도 그대로 남는다.

## 3. 현재 기준 문서

정리 후 `docs` 최상위에는 아래 문서만 둔다.

| 문서 | 역할 |
|---|---|
| `README.md` | 문서 지도와 우선순위 |
| `PRODUCT_BRIEF.md` | 제품 목적, 사용자, 안전 경계 |
| `PRD.md` | 현재 프로토타입 요구사항과 완료 조건 |
| `UX_SPEC.md` | 보호자 여정과 화면 동작 |
| `TECHNICAL_OVERVIEW.md` | 실제 구현 기준 아키텍처, API, 저장소, 실행 방법 |
| `SECURITY_PRIVACY.md` | 개인정보와 의료 안전 기준 |
| `REFERENCES.md` | 병원·의료 콘텐츠·기술 근거 |

`TECHNICAL_OVERVIEW.md`는 현재 코드만 설명한다. 보호자 여정은 메모리
저장소를 사용하고, 검사·수술 카탈로그만 PostgreSQL 기반이 준비되어
있다는 차이를 명시한다. 실제 EMR, 병원 지도, Voice EMR 연동은
구현된 것으로 표현하지 않는다.

## 4. 아카이브 구조

### `docs/archive/preparation-orchestration`

이전 검사·수술 준비 누락 방지 제품 트랙의 아래 문서를 이동한다.

- `API_SPEC.md`
- `ARCHITECTURE.md`
- `DATABASE.md`
- `DOMAIN_MODEL.md`
- `INFRASTRUCTURE.md`
- `PROTOTYPE_PLAN.md`
- `QA_PLAN.md`
- `TEAM_PLAN.md`
- 검사·수술 준비 오케스트레이션 설계
- MVP 기반 및 카탈로그 구현 계획

### `docs/archive/process`

이미 완료되어 현재 요구사항의 기준이 아닌 작업 기록을 이동한다.

- PR 템플릿 설계와 구현 계획
- 보호자 여정 프로토타입 설계와 구현 계획
- 이 문서 정리 설계와 구현 계획

각 아카이브에는 `README.md`를 두어 해당 문서가 현재 요구사항이나
구현 상태의 기준이 아님을 표시한다.

## 5. 링크와 소유권

- 저장소 `README.md`는 현재 기준 문서만 연결한다.
- `docs/README.md`는 최상위 기준 문서와 아카이브를 구분한다.
- 이동된 문서의 역사적 내용은 수정하지 않는다.
- 현재 기능 변경 시 `PRD.md`, `UX_SPEC.md`,
  `TECHNICAL_OVERVIEW.md` 중 영향받는 문서만 갱신한다.
- API 요청·응답의 최종 실행 계약은
  `packages/contracts`의 Zod 스키마와 API 테스트로 검증한다.

## 6. 완료 조건

- `docs` 최상위에 현재 기준 문서 7개만 남는다.
- 이전 트랙과 완료된 작업 기록이 지정된 아카이브에 있다.
- 현재 README 링크가 모두 유효하다.
- `TECHNICAL_OVERVIEW.md`가 현재 코드와 일치한다.
- `TBD`, `TODO` 또는 구현 여부가 불명확한 표현이 없다.
- 테스트, 타입 검사, 빌드와 Markdown 링크 검사가 통과한다.
