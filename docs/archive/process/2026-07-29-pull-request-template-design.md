# 제품·개발 통합형 Pull Request 템플릿 설계

## 1. 목적

Ready:ON의 Pull Request가 코드 변경만 설명하지 않고 다음 정보를 한 번에 전달하도록 한다.

- 어떤 사용자 문제를 해결하는가
- 제품 요구사항과 어떤 관계가 있는가
- 구현 범위와 제외 범위는 무엇인가
- 데이터베이스, 보안, 의료 안전에 미치는 영향은 무엇인가
- 어떤 자동·수동 검증을 통과했는가
- 리뷰어가 집중해서 확인할 부분은 무엇인가

## 2. 적용 방식

저장소 기본 템플릿은 `.github/pull_request_template.md` 한 개를 사용한다.

여러 템플릿을 선택하게 하지 않는 이유:

- 5명 팀이 동일한 검토 순서를 사용하게 한다.
- 프로토타입 단계에서 템플릿 선택 비용을 만들지 않는다.
- 기능, 수정, 문서 PR 모두 불필요한 항목을 `해당 없음`으로 명시할 수 있다.

## 3. 템플릿 구조

### 3.1 변경 목적

- 해결하려는 문제
- 사용자 또는 운영자에게 생기는 변화

### 3.2 변경 내용

- 주요 구현 사항
- 의도적으로 포함하지 않은 사항

### 3.3 관련 문서

- PRD 요구사항 ID
- 설계, 이슈 또는 참고 문서 링크

관련 문서가 없으면 `해당 없음`을 적는다.

### 3.4 검증

실행한 명령과 결과를 직접 적는다.

- test
- typecheck
- build
- lint
- 수동 확인

실행하지 않은 항목은 체크하지 않는다.

### 3.5 데이터베이스와 API

- migration 추가 여부
- 하위 호환성
- rollback 또는 복구 방법
- API 계약 변경 여부

DB와 API를 변경하지 않으면 `해당 없음`을 적는다.

### 3.6 보안·개인정보·의료 안전

체크 항목:

- 실제 환자정보를 포함하지 않음
- 비밀정보를 커밋하지 않음
- 인증·권한·조직 격리를 검토함
- 의료지침을 임의로 생성하거나 변경하지 않음
- `READY`를 임상 판단으로 표현하지 않음

해당 검토가 필요한 변경인데 확인하지 않았다면 PR을 Ready 상태로 전환하지 않는다.

### 3.7 화면 변경

- 스크린샷 또는 영상
- 접근성 확인
- 반응형 확인

UI 변경이 없으면 `해당 없음`을 적는다.

### 3.8 배포와 운영

- 환경변수 변경
- 배포 순서
- 모니터링 또는 health check 영향
- rollback 방법

### 3.9 리뷰 요청

리뷰어가 우선 확인할 파일, 규칙 또는 위험을 작성한다.

## 4. 작성 규칙

- 체크박스는 실제 확인한 항목만 선택한다.
- 긴 변경 이력을 붙여 넣지 않고 현재 PR의 결과를 요약한다.
- 테스트 통과 여부는 실행한 명령과 결과 수치를 함께 적는다.
- 실제 환자명, 진단, 검사 결과와 토큰을 PR 본문이나 스크린샷에 넣지 않는다.
- Draft PR은 미완료 항목과 다음 작업을 명시한다.

## 5. 현재 브랜치 PR 기준

`feat/mvp-foundation`은 아직 전체 카탈로그 UI가 완료되지 않았으므로 Draft PR로 생성한다.

본문에 포함할 완료 범위:

- TypeScript npm workspace
- Zod 공유 계약
- NestJS health API
- Supabase PostgreSQL migration
- Drizzle schema
- 카탈로그 도메인 서비스
- 요청별 RLS transaction
- PostgreSQL 17 통합 테스트

미완료 범위:

- Supabase JWT 인증
- 카탈로그 REST controller
- 의료진 카탈로그 웹 화면
- Vercel·OCI 배포

## 6. 완료 조건

- `.github/pull_request_template.md`가 GitHub 기본 PR 템플릿으로 인식된다.
- 템플릿에 제품, 검증, DB/API, 보안·의료 안전, UI, 배포, 리뷰 요청 섹션이 있다.
- 현재 브랜치 Draft PR이 템플릿 구조를 사용한다.
- PR 본문의 테스트 결과가 실제 최신 검증 결과와 일치한다.
- 기존 `main`을 base, `feat/mvp-foundation`을 head로 사용한다.
